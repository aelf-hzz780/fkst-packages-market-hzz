sequentially takes over the same stable `auto-x-hzz780` label.

启动 RC Session 前，必须停止所有接管同一 repo、账号或 work label 的旧 Session。Package
支持顺序接管后的恢复，但不为两个并发首次执行提供 distributed lease。RC 验收结束后，也必须

## Acceptance sequence / 验收步骤

### Phase A: proposal Shadow / 提案 Shadow

1. Start only the isolated RC Session and record its task ID, effective label, package descriptor,
   and Environment Profile name.
2. Submit the four copies. Do not create any `schedule-publish` Issue.
3. Wait until each Signal has an `awaiting-review` status and inspect the generated proposals.
4. Replay one unchanged Signal event and restart the Session once. Verify that neither action creates
   another active Proposal.
5. Submit an account-mismatch copy with `account: aelfblockchain` under the hzz780 route. Verify a
   `needs-triage: account-session-mismatch` response and `publish_attempted: false`. A
   `blocked/unrouted` response is reserved for a safely routed Issue whose expected account/Profile
   authority is missing or conflicting.
6. Record the exact tweet text, proposal ID, and current revision for both Proposals. At this gate,
   there must still be zero approved Content Issues and zero Schedules.

1. 只启动隔离的 RC Session，并记录 task ID、effective label、package descriptor 与 Environment
   Profile 名称。
2. 提交四个副本，不创建任何 `schedule-publish` Issue。
3. 等待每个 Signal 进入 `awaiting-review`，并检查生成的 Proposal。
4. 重放一个未变化的 Signal event，并重启一次 Session；两种操作都不能创建新的 active Proposal。
5. 在 hzz780 route 下提交一份 `account: aelfblockchain` 的错账号副本，确认收到
   `needs-triage: account-session-mismatch`，且 `publish_attempted: false`。`blocked/unrouted`
   仅用于 Issue 已安全路由，但预期账号或 Profile authority 缺失或冲突的情况。
6. 记录两个 Proposal 的完整 tweet text、proposal ID 与 current revision。此门禁时仍必须保持
   approved Content 为零、Schedule 为零。

### Phase B: simulated COO review / 模拟 COO 审核

7. As the authorized `aelf-hzz780` reviewer, request changes on the current W33 revision with a
   concrete evidence or CTA reason. Verify that the same Proposal receives the next immutable
   revision and no Content Issue is created.
8. Submit an approval for the superseded W33 revision and verify that it fails closed as stale.
9. Approve the latest W33 revision and the current W34 revision. Approval may create approved
   immutable `weekly-content` Issues, but it must not create a Schedule or publish request.
10. Verify exactly two approved Content Issues. The four copied Signals and two Proposals must be
    terminally acknowledged and closed after fresh digest validation. Keep the mismatch fixture Open.

7. 使用授权 reviewer `aelf-hzz780` 对 W33 current revision 发出带明确证据或 CTA 理由的
   request-changes；确认同一 Proposal 生成下一个不可变 revision，且不创建 Content。
8. 对已被替代的 W33 revision 提交 approve，确认其按 stale revision fail closed。
9. 批准 W33 latest revision 与 W34 current revision。Approve 只允许生成已审核、不可变的
   `weekly-content`，不得创建 Schedule 或 publish request。
10. 确认恰好两个 approved Content；四个 Signal 副本与两个 Proposal 在 fresh digest 校验后
    完成终态 ACK 并关闭。错账号负测 Issue 保持 Open。

## Pass criteria / 通过标准

- `#116/#117/#118` copies converge to exactly one W33 `weekly-plan-change` Proposal.
- The `#124` copy creates exactly one W34 Proposal.
- Phase A has exactly two active Proposals and zero approved Content Issues.
- Phase B has exactly two immutable approved Content Issues; the two Proposals and four copied
  Signals are closed, while no Schedule, `x_publish_request`, or `POST /tweets` call exists.
- Replay and sequential Session restart do not create a duplicate Proposal.
- Account mismatch, stale revision, unauthorized review, and invalid target all fail closed.

- `#116/#117/#118` 副本最终只形成一个 W33 `weekly-plan-change` Proposal。
- `#124` 副本只形成一个 W34 Proposal。
- Phase A 严格为两个 active Proposal、零 approved Content。
- Phase B 严格为两个不可变 approved Content，两个 Proposal 与四个 Signal 副本均已关闭；
  同时 Schedule、`x_publish_request` 与 `POST /tweets` 全部为零。
- 重放与顺序重启 Session 不产生重复 Proposal。
- 账号错配、旧 revision、未授权审核与非法 target 全部 fail closed。

Capture the two Proposal URLs and revision history, two Content URLs, Signal status comments,
Session logs showing zero publish requests, and the account-mismatch evidence. Do not include
credentials in the evidence bundle.

验收证据需包含两个 Proposal URL 及 revision 历史、两个 Content URL、Signal 状态评论、证明
零 publish request 的 Session 日志，以及账号错配结果；证据包不得包含 credential。

## Canary and rollback / Canary 与回滚

A live canary is a separate approval. Before it, review the exact `hzz780` account, final tweet text,
Content digest, Schedule body, Environment Profile, and execution time. Enable the live write gate
only for that confirmed canary.

真实 Canary 需要单独确认。执行前必须再次核对 `hzz780` 账号、最终文案、Content digest、
Schedule body、Environment Profile 与执行时间；只为已确认的 Canary 临时开启 live write gate。

Shadow completion never authorizes the canary automatically. Record an explicit approval after the
exact tweet text and target account are shown to the operator; without that approval, keep both X
write gates disabled and create no live Schedule.

Shadow 通过不会自动授权 Canary。必须先向运营人员展示最终 tweet text 与目标账号，并记录一条
独立的明确批准；没有该批准时，两个 X write gate 必须继续关闭，且不得创建 live Schedule。

To roll back, stop the RC Session, keep generated v2 Issues frozen, and restore the v0.2.2 Session
on its previous label. Never run v0.2.2 and v0.3.0 against the same label, and never delete or mutate
an already published X post.

回滚时停止 RC Session，冻结已生成的 v2 Issue，并在原 label 上恢复 v0.2.2 Session。禁止
v0.2.2 与 v0.3.0 共用同一 label，也不得删除或修改已经发布的 X Post。
