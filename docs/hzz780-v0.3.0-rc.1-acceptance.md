# hzz780 v0.3.0-rc.1 acceptance runbook

This runbook validates the Auto Twitter v0.3.0 review workflow with the `hzz780` X account. It is
an isolated Shadow acceptance procedure. It does not authorize a live X write.

本文用于使用 `hzz780` X 账号验收 Auto Twitter v0.3.0 review workflow。该流程是隔离的
Shadow 验收，不代表已经授权真实 X 写入。

For this RC, Shadow temporarily uses `hzz780`. The four referenced production Issues remain source
evidence only: acceptance operates on isolated copies whose `account` is normalized to `hzz780`.
`aelfblockchain` is used only as an account-mismatch negative test.

本次 RC 的 Shadow 暂时使用 `hzz780`。下述四个生产 Issue 只作为来源证据；验收仅操作隔离
副本，并把副本的 `account` 统一归一为 `hzz780`。`aelfblockchain` 只用于账号错配负测。

## Scope / 范围

The acceptance target is `aelf-hzz780/fkst-packages-market-hzz@v0.3.0-rc.1`. The official
`github-proxy` is imported separately. No `fkst-hosted` or official package code is changed.

验收目标为 `aelf-hzz780/fkst-packages-market-hzz@v0.3.0-rc.1`，official `github-proxy`
单独导入。本流程不修改 `fkst-hosted` 或 official package 代码。

| Identity / 标识 | Acceptance value / 验收值 |
|---|---|
| X account | `hzz780` |
| GitHub Session creator | `aelf-hzz780` |
| Logical and isolated work label | `auto-x-hzz780` |
| Package descriptor | `aelf-hzz780/fkst-packages-market-hzz@v0.3.0-rc.1:manifests/auto-twitter-marketing.json` |
| X write gates | disabled / 关闭 |

## Preconditions / 前置条件

Stop every older Session that owns the same repository, account, or work label before starting the
RC Session. The package provides sequential takeover recovery, not a distributed lease for two
simultaneous first attempts. After RC acceptance, stop the RC Session before a stable Session
sequentially takes over the same stable `auto-x-hzz780` label.

启动 RC Session 前，必须停止所有接管同一 repo、账号或 work label 的旧 Session。Package
支持顺序接管后的恢复，但不为两个并发首次执行提供 distributed lease。RC 验收结束后，也必须
先停止 RC Session，再由 stable Session 顺序接管同一个稳定的 `auto-x-hzz780` label。

Create or select the `hzz780` Environment Profile and verify that its NyxID X service resolves
`/users/me` to `hzz780`. Keep both write gates disabled for Shadow acceptance:

创建或选择 `hzz780` Environment Profile，并确认其 NyxID X service 调用 `/users/me` 返回
`hzz780`。Shadow 验收期间必须关闭两个 write gate：

```text
X_PUBLISH_EXPECTED_USERNAME=hzz780
X_PUBLISH_WRITE=0
FKST_X_PUBLISH_WRITE=0
NYXID_X_SERVICE_SLUG=<hzz780-service-slug>
```

The service slug belongs in the user Environment Profile. Tokens and credentials must never be
placed in this document, an Issue, a manifest, a comment, or a log.

Service slug 只配置在用户 Environment Profile 中。Token 与 credential 不得写入本文、Issue、
manifest、comment 或 log。

Configure one Hosted Session with `### Work Label` set to `auto-x-hzz780`. Verify that the Host
injects `FKST_SESSION_CREATOR=aelf-hzz780` and that the logical-to-effective label mapping resolves
back to `auto-x-hzz780`.

创建唯一的 Hosted Session，并把 `### Work Label` 设置为 `auto-x-hzz780`。确认 Host 注入
`FKST_SESSION_CREATOR=aelf-hzz780`，且 logical-to-effective label mapping 能反向解析为
`auto-x-hzz780`。

“不要修改”包括 label、assignee、account 字段、正文、评论与状态。原 Issue 不迁移到 RC

Each copy must use the v2 controls below. Preserve the original evidence in the trusted narrative or

每个副本必须使用以下 v2 controls。原始证据保留在可信正文或 `source-url` 中，但验收账号与
route 必须显式改写。三个 W33 副本使用同一个由运营确认的 canonical topic；W34 单独成组。

## Acceptance sequence / 验收步骤

1. Start only the isolated RC Session and record its task ID, effective label, package descriptor,
   and Environment Profile name.
2. Submit the four copies. Do not create any `schedule-publish` Issue.
3. Wait until each Signal has an `awaiting-review` status and inspect the generated proposals.
4. Replay one unchanged Signal event and restart the Session once. Verify that neither action creates
   another active Proposal.
5. Submit an account-mismatch copy with `account: aelfblockchain` under the hzz780 route. Verify a
   `needs-triage: account-session-mismatch` response and `publish_attempted: false`. A
   `blocked/unrouted` response is reserved for a safely routed Issue whose expected account/Profile
   authority is missing or conflicting.
6. Leave all proposals unapproved during Shadow acceptance.

1. 只启动隔离的 RC Session，并记录 task ID、effective label、package descriptor 与 Environment
   Profile 名称。
2. 提交四个副本，不创建任何 `schedule-publish` Issue。
3. 等待每个 Signal 进入 `awaiting-review`，并检查生成的 Proposal。
4. 重放一个未变化的 Signal event，并重启一次 Session；两种操作都不能创建新的 active Proposal。
5. 在 hzz780 route 下提交一份 `account: aelfblockchain` 的错账号副本，确认收到
   `needs-triage: account-session-mismatch`，且 `publish_attempted: false`。`blocked/unrouted`
   仅用于 Issue 已安全路由，但预期账号或 Profile authority 缺失或冲突的情况。
6. Shadow 验收期间不批准任何 Proposal。

## Pass criteria / 通过标准

- `#116/#117/#118` copies converge to exactly one W33 `weekly-plan-change` Proposal.
- The `#124` copy creates exactly one W34 Proposal.
- Total output is exactly two active Proposals, zero approved Content Issues, zero Schedules, and
  zero `POST /tweets` calls.
- Replay and sequential Session restart do not create a duplicate Proposal.
- Account mismatch, stale revision, unauthorized review, and invalid target all fail closed.

- `#116/#117/#118` 副本最终只形成一个 W33 `weekly-plan-change` Proposal。
- `#124` 副本只形成一个 W34 Proposal。
- 总结果严格为两个 active Proposal、零 approved Content、零 Schedule、零 `POST /tweets`。
- 重放与顺序重启 Session 不产生重复 Proposal。
- 账号错配、旧 revision、未授权审核与非法 target 全部 fail closed。

Capture the two Proposal URLs, Signal status comments, Session logs showing zero publish requests,
and the account-mismatch evidence. Do not include credentials in the evidence bundle.

验收证据需包含两个 Proposal URL、Signal 状态评论、证明零 publish request 的 Session 日志，
以及账号错配结果；证据包不得包含 credential。

## Canary and rollback / Canary 与回滚

A live canary is a separate approval. Before it, review the exact `hzz780` account, final tweet text,
Content digest, Schedule body, Environment Profile, and execution time. Enable the live write gate
only for that confirmed canary.

真实 Canary 需要单独确认。执行前必须再次核对 `hzz780` 账号、最终文案、Content digest、
Schedule body、Environment Profile 与执行时间；只为已确认的 Canary 临时开启 live write gate。

Shadow completion never authorizes the canary automatically. Record an explicit approval after the
exact tweet text and target account are shown to the operator; without that approval, keep both X
write gates disabled and create no live Schedule.

Shadow 通过不会自动授权 Canary。必须先向运营人员展示最终 tweet text 与目标账号，并记录一条
独立的明确批准；没有该批准时，两个 X write gate 必须继续关闭，且不得创建 live Schedule。

To roll back, stop the RC Session, keep generated v2 Issues frozen, and restore the v0.2.2 Session
on its previous label. Never run v0.2.2 and v0.3.0 against the same label, and never delete or mutate
an already published X post.

回滚时停止 RC Session，冻结已生成的 v2 Issue，并在原 label 上恢复 v0.2.2 Session。禁止
v0.2.2 与 v0.3.0 共用同一 label，也不得删除或修改已经发布的 X Post。
